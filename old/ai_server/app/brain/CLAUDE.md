# app/brain/ — the companion brain

`CompanionBrain.respond(CompanionTurn) -> CompanionReply`. Intent classification, dialogue, candidate actions, and any state needed across turns. See the root [CLAUDE.md](../../CLAUDE.md) for the project and [../CLAUDE.md](../CLAUDE.md) for the transport edge that calls this.

Import rule: `app.models`, `app.settings`, and the pure `app.gamedata` dataset leaf are allowed; FastAPI, Starlette, SQLAlchemy, routes and request-context state are not. This is intelligence, not transport.

## The turn pipeline

0. Routing is a LangGraph `StateGraph` compiled once in `CompanionBrain.__init__` (`graph.py`); `respond` `ainvoke`s it and maps the final state to `CompanionReply`. Nodes are plain async Python closures — **no LangChain chat-model wrappers**; `LLMProvider` and the fact stores are untouched.

0.5. **Multi-turn is a conditional entry point, not a third routing stage.** If the store holds a `PendingSlot` for this `conversation_key`, `resolve_pending` runs first: an answer fills the gather slot (reviving the pending quantity) and routes straight to `gather`, **skipping both stages below** (`resolve_pending` + `generate_dialogue` = 2 calls, one *fewer* than an ordinary gather turn); a change of subject drops the slot and falls through to `classify_top`, which is the only case that costs an extra call. With no pending slot the path is byte-for-byte the one below. The slot is set **only** by `gather_node`'s ask-back and is otherwise cleared every turn — a node that does not write `next_pending` forgets, so a slot can never quietly outlive its question. A slot is carried forward (`asked_again`) only when `pending_answered` is true; a fresh gather request builds a new one, or last turn's quantity leaks into it.

1. `turn.text` (Korean) runs Stage 1 `classify_top` → `command / recipe / lore / conversation / unknown`. A `command` runs Stage 2 `classify_command`, which returns a `CommandClassification` carrying the label (`follow_player / wait / stop_current_task / gather_resource / attack / return_to_player / unknown`) **plus the gather slots** `resource` (`wood / stone / other / unspecified`) and `quantity` (`int | None`) — unused for every label but `gather_resource`. The slots ride along on the existing call rather than getting a classifier of their own.

2. **Action mapping** (only when the mapped type is in `turn.allowed_actions`): `follow_player→Action.Follow`, `wait→Action.HoldPosition`, `stop_current_task→Action.CancelCurrent`, `gather_resource→Action.GatherResource`, `attack→Action.Attack`, `return_to_player→Action.Switch`. Cancel utterances such as `"됐어"` and `"취소"` are classified as `stop_current_task`. **`attack` resolves its target from the raw utterance, not a classifier slot**: `EnemyRepository.resolve_target` reuses the same alias-matching `fact_for` already does, and the result (or its absence) rides in `CompanionAction.parameters["target_id"]` — never the wire's top-level `CommandCandidate.target_id`, which stays unpopulated (`docs/backlog/future_features.md`'s Entity Resolver is still future work). recipe, lore, conversation, and unknown return **`text` only**, no action.

3. **When a mapped action is not in `allowed_actions`, the node must not render its acceptance line** — it routes to the `unsupported` scene instead. Emitting "알겠어, 따라갈게" with no command would make Mako promise something the game never receives.

4. **gather slots are owned in layers**: the LLM picks a constrained `ResourceSlot` enum (it cannot invent a resource name), `ResourceRepository` decides which slots are actually supported and what the quantity ceiling is, and `GatherParameters` validates the pair before it reaches `CompanionAction.parameters` (`{"resource": "wood", "quantity": 20}`). **Quantity is optional by design**: if the player did not say a number, the key is omitted and the game picks its own amount — the server has no inventory/durability context to guess with, and a made-up number would leak into dialogue. Out-of-range quantities and unsupported resources produce dialogue with no action, never a clamped one.

5. Dialogue always goes through `dialogue.render` (scene guide + code-verified facts, turn-scoped situation, `sanitize` length/number guard, fallback template on any failure). Metadata reports provider/model/prompt version. **This is the only layer a `Surface` and game time reach** — `say()` copies `turn.surface` and `turn.game_time` onto the spec, the provider swaps one tone block into the system prompt, and `SURFACE_PROFILES` supplies the refusal lines. See "One pipeline, two surfaces" below.

6. **The last few turns ride in the dialogue prompt only.** `say()` takes the whole state so every scene gets `history` from one place; the routing nodes (`classify_top` / `classify_command` / `resolve_pending`) never see it — if history reached a classifier, a `"따라와"` from three turns ago could fire a command now. History buys tone continuity and stops Mako repeating a line verbatim; it is **not** a fact source. See "History is not a fact source" below.

7. **Long-term memory rides the same path, one block earlier.** `CompanionBrain.respond` recalls before invoking the graph and puts the chosen sentences on `state["long_term"]`; `say()` passes them as `DialogueSpec.memories` and they render as `[기억]`, ahead of optional `[상황]` and `[최근 대화]`. The turn then appends the two lines just spoken to the **transcript** and returns. Extraction, summarising and consolidation are LLM calls that **never run inside a turn** — a single background loop drains them, so a turn still costs the same 2–3 calls. See "Memory rules" below.

## History is not a fact source

`sanitize` admits only numbers from `spec.facts`, so a model that tries to answer from the transcript is rejected and falls back. **That guard is numeric only** — a false *non-numeric* claim a player made ("여기는 용의 둥지야") can still be echoed. The same is true of the `[기억]` block, and worse in one respect: a false claim that got extracted into long-term memory outlives the conversation it was made in. The bounds on that are the extractor prompt ("게임 정보는 기억하지 않는다"), the digit ban, the per-player cap, and the fact that memories can never reach `facts`. This is not new to history: the current utterance has ridden in the prompt as `[플레이어] …` from the start, and the `conversation` scene skips the numeric check entirely. Unverified player text in prompts is inherent to a chat companion; the defenses are the prompt instruction, the numeric guard, the per-turn caps, and the fallback. Closing it properly means fact-checking generated claims, which is a larger piece of work than this layer — do not pretend a prompt line guarantees it.

That is deliberate: anaphora like `"그거 재료가 뭐라고?"` still lands on `unsupported`, because `RecipeRepository` is keyed on the current utterance and facts must come from a verified store, never from prompt history. Resolving referents means teaching the repositories about history — a separate, deliberate step.

## One pipeline, two surfaces

Mako answers from inside the game (standing next to the player) and from a phone chat. **There is one pipeline.** Routing, the ask-back multi-turn, the verified fact stores and all three memory layers are surface-independent; duplicating them would let the two classifiers drift until the same sentence became a different command depending on where it was typed. What actually differs is not *what is judged* but *how it is said*, and that already lives in one place.

So `Surface` and `game_time` (`app/models.py` — `app.models` is a leaf both halves may import) ride `ChatRequest` → `CompanionTurn` → `DialogueSpec`; `game_time` is prompt-only, while `surface` also selects the surface fallback lines. Concretely:

- `say()` is the only place *inside the routed graph* that reads `turn.game_time`/`turn.surface` (`profile()` also reads `turn.surface`, for fallback wording); `situation.py`'s `build_spec` is the analogous single reader for the unrouted `SituationTurn` path (below). The classifiers take a `str` and have no parameter to receive either value. Presentation or turn context reaching a classifier would be the same mistake as history reaching one.
- `SURFACE_PROFILES` holds one `SurfaceProfile` per surface: a `tone` block spliced into `llm.py`'s `_DIALOGUE_PROMPT_TEMPLATE`, plus the lines Mako says when it *cannot* help. Those are `FallbackLine(text, fact)` pairs because the two must change together — the game's `"가능한 일은 따라오기, 대기, 작업 중지뿐이다"` is a **false fact** on a phone, and shipping it as dialogue-only would leave it in the prompt.
- `SCENE_GUIDE` is deliberately **not** split. A scene guide says *what to convey*, which does not vary by surface; only *how* does, and that is `tone`.
- `sanitize` does not look at the surface. The length cap and the numeric guard are safety nets, not voice.
- `MockLLMProvider.generate_dialogue` returns `spec.fallback` and nothing else, so the fallback is the single source of every surface's wording. A rule-based imitation would have to be split per surface too, and would still not resemble what a real provider says.

**The surface never decides whether Mako may act — `allowed_actions` does, alone.** Mobile emits no command unless the mobile client actually sends `allowed_commands: ["Command.GatherResource"]` — nothing here special-cases it, so the client must opt in itself. What differs for mobile is not routing but what happens *after* the brain replies: `CompanionService.create_response` (`app/service.py`) checks `identity.role` (not `surface` — that stays presentation-only) and, for a `WEB_CLIENT`-authenticated device whose `CompanionReply.action.type` is `GATHER_RESOURCE`, creates an `Offline_Task` (`OfflineTaskType.GATHERING`) instead of a `CommandCandidate` — there is no live GameClient in that conversation to hand a command to. `_COMMANDS` / `_GATHER_SCENES` / `gather_node` stay untouched by this; the brain still only ever judges "gather intent + resource + quantity," identical for both surfaces. Any `surface == mobile` branch written outside `SURFACE_PROFILES` would have to be unwound — the mobile/task-issuing distinction above lives in `app/service.py` precisely to avoid that.

## Situation events — a second entry point

`CompanionBrain.react(SituationTurn) -> str` (`companion.py`) answers `POST /api/v1/situations`. It exists because a client-triggered situation is **already classified** — the game decided in code that "player HP low" or "enemy sighted" just happened, and told the server so. Re-running Stage 1/2 classification on a sentence the *server itself would have to write* is pure waste, so `react` skips `graph.py` entirely: no `classify_top`, no `classify_command`, one `generate_dialogue` call.

- `contract.py`'s `SituationTurn` mirrors `CompanionTurn`'s identity fields (`conversation_key`, `player_key`, `companion_id`, `surface`, `game_time`) but has no `text`/`allowed_actions` — there is nothing to classify and nothing to gate, so `react` returns a bare `str`, not a `CompanionReply`. It has its own `situation: tuple[str, ...]` (the client's free-text lines) instead.
- `situation.py`'s `build_spec` is the prompt-assembly leaf for this path, the same weight class as `gametime.py`: it sets `scene="situation"`, `user_text=None` (no player utterance), `facts=()` (no verified-fact lookup — the situation already *is* the "fact," rendered as `[상황]` alongside the game clock via `gametime.describe`), and passes through `history`/`memories` unchanged.
- **`react` never touches `pending`.** `respond` overwrites the ask-back slot with `next_pending` every turn specifically so a slot never silently survives past the node that should own it; a situation event is not an answer to that ask-back, so if it wrote `next_pending` at all it would have to write `None`, deleting an in-flight "무엇을 캘까?" the moment an unrelated situation fires. `store.py`'s `ConversationMemory.reacted()` is the narrower alternative: it appends to `recent_turns` and leaves `pending` exactly as it was.
- **A third `ConversationTurn`/`TranscriptEntry` speaker, `"situation"`**, alongside `"player"`/`"companion"` (`store.py`, `transcript.py`). Long-term memory is read *and written* for situation events (unlike a hypothetical read-only design), so the extraction/summary prompts and `[최근 대화]` need to distinguish "the player said this" from "the client reported this happened" — conflating them would let a false player claim and a true client-reported situation look identical to the memory extractor. `llm.py`'s `_SPEAKER_LABELS` (`"상황"`) is the one place that has to know about the new value; `_dialogue_user_message` needed no change beyond that, since it already keys off `_SPEAKER_LABELS` generically.
- `CompanionService.create_situation_response` (`app/service.py`) is `create_response`'s sibling, not a variant of it — same `identity.validate_claims` → `COMPANION_PROFILES` membership → `SaveSlotRepository.get_or_create` → timeout-wrapped brain call shape, but no `_assert_within_allowlist` (nothing to assert) and no Offline_Task branch (no action to convert). It reuses `_conversation_key`/`_player_key`, which is why those two took explicit `profile_id=`/`save_slot_id=`/… keyword arguments instead of a `ChatRequest` — a chat turn and a situation event with the same four scope values must land in the same conversation, and a function typed to accept only `ChatRequest` couldn't do that.

## Module responsibilities

- `contract.py` — what the brain takes and returns: `CompanionTurn` (text, `allowed_actions`, `location_id`, `game_time`, `conversation_key`, `companion_id`), `CompanionReply`, `CompanionAction`, and `SituationTurn` (situation events — see above). It deliberately carries **no** `request_id`/`expires_at`: those are wire ledger, not Mako's judgment, and `service.py` stamps them. Actions are typed with `CommandType` from `app/models.py` — a separate `ActionType` used to redeclare four of its values, which cost a subset test and a conversion to keep in step. `companion_id` defaults to `""` like `player_key` and is, for now, pure plumbing: `service.py` validates membership in `companions.py`'s `COMPANION_PROFILES` before the turn is built, but no node in `graph.py` branches on it and `llm.py`'s prompts are still hardcoded to Mako. See `companions.py` below.
- `companion.py` — `CompanionBrain`: builds the graph once, recalls long-term memory, loads the conversation's working memory, `ainvoke`s the graph, saves what it returns, serialises per-conversation with a refcounted lock, appends the turn to the transcript, and owns the **distillation queue and its background loop**. `respond(CompanionTurn)` is the routed path; `react(SituationTurn)` (above) is the unrouted one — they share `_recall`/`_record`, which take explicit `player_key`/`conversation_key`/`turns` rather than a `CompanionTurn` so both callers can use them. **Converts no exceptions** — swallowing them here would stop `service.py` telling an outage apart from a normal answer; the memory pipeline (`_record`, `_drain`) is the documented exception, because a background task has no caller to raise to. Reads no `Settings`; takes prebuilt stores and its bounds as arguments.
- `situation.py` — `build_spec(SituationTurn, *, history, memories) -> DialogueSpec`, the prompt-assembly leaf for situation events (above).
- `transcript.py` — `TranscriptEntry` / `TranscriptStore` protocol (`append` / `read` / `tail` / `sweep`) + `FileTranscriptStore`: append-only JSONL per `conversation_key`, monotone `seq`, `sweep` deleting files past the retention. **The only layer that grows without bound**, so the sweep is part of the design, not housekeeping. A broken line costs only that line (an append-only log's last line can be a torn write) — unlike a memory file, which is rewritten whole and so is distrusted whole. `speaker` is `Literal["player", "companion", "situation"]`.
- `store.py` — `PendingSlot` / `ConversationTurn` / `ConversationMemory` / `ConversationStore` + `InMemoryConversationStore`. The brain's own working memory, keyed by the opaque `conversation_key`. Lifetimes are **two-layered**: the conversation entry expires on an idle TTL (`conversation_idle_ttl_seconds`, default 30 min) and the ask-back slot expires sooner inside it (`pending_ttl_seconds`, default 2 min) — merging them would either strand history-only entries forever or cut conversations short. `PendingSlot` carries the **already-stated quantity** so `"저것 20개 캐 줘"` → `"뭘 캐?"` → `"나무"` still yields `quantity: 20`, and an `ask_count` capped at `MAX_ASK_COUNT` so a player who keeps answering vaguely does not get the same question forever. `ConversationMemory.appended` (chat) and `.reacted` (situation events, above) are the only two writers; `reacted` is the one that leaves `pending` untouched.
- `graph.py` — the routing `StateGraph`: `CompanionState` / `CompanionUpdate` TypedDicts, `build_companion_graph(llm, recipes, lore, resources, enemies)` (dependencies captured as closures, not `RunnableConfig`), pure conditional-edge functions `route_by_top` / `route_by_command` (`Literal` return types so LangGraph infers topology), the `_COMMANDS` and `_GATHER_SCENES` tables (label/resource → `CommandType` + scene + fallback), and the `allowed_actions` gate with its `decline` helper. `attack` gets its own node rather than a `_COMMANDS` row because it needs `EnemyRepository.resolve_target` to fill an optional target, the same reason `gather` isn't in that table either; `return_to_player` has no such need and sits in `_COMMANDS` like `follow_player`/`wait`/`stop_current_task`. Terminal nodes: `movement_command`, `attack`, `gather`, `recipe`, `enemy`, `lore`, `conversation`, `unsupported` — every one fills `display_text`. Situation events never enter this graph.
- `memory.py` — long-term memory: `LongTermMemory` (kind / text / keywords / importance / embedding / `source_key` / `recalled_at` / `recall_count`), `build_memory` (the only way to make one, and the place the digit ban and length cap live), `strength` (importance 1~10 normalized to the old score ceiling, decayed by a 30-day half-life, plus a capped recall bonus), `rank` (keyword overlap + optional semantic similarity + strength, ties broken by recency then kind), `merge` (same-text replace **inheriting old recall history and vectors**, one `session_summary` per `source_key`, evict weakest), `consolidated` (turns a `Consolidation` into memories that inherit their sources' history), the four spec/result models, `LongTermStore` protocol, and legacy JSON read compatibility for migration. The runtime store is `app/episodic_memory_store.py` backed by SQLite; it opens its own session per operation so the singleton brain's background loop can use it. `app/brain/embedding.py` contains only the provider interface; concrete OpenAI/Local/mock construction lives in `app/embedding.py` outside the brain boundary.
- `llm.py` — `LLMProvider` interface (`classify_top`, `classify_command`, `resolve_pending`, `generate_dialogue`, `extract_memories`, `summarize_session`, `consolidate_memories`), `MockLLMProvider` (default, deterministic regex routing + scene fallbacks; also the fallback for real providers), `OpenAIProvider` (Responses API), `LocalLLMProvider` (OpenAI-compatible Chat Completions). The only module that reads `Settings`. `build_llm_provider(settings)` returns a `SelectedProvider` (provider **plus** the name/model it chose, so callers never re-derive the selection rule and drift); it picks `local`/`openai` only when `provider` matches **and** the key is set, else `mock`. Any provider failure silently falls back to mock. **Mock returns an empty result for all three memory methods** — what is worth remembering is not a judgment a regex can imitate, and a fake rule would quietly store something unlike what the real providers store. So the default configuration never creates a long-term memory, and tests that exercise the layer supply an explicit stub. `_SPEAKER_LABELS` includes `"situation": "상황"`.
- `command_intent.py` — `CommandIntentParser` + shared regexes: `classify_simple_command()` (follow/wait/stop), `resolve_gather()` (`ResourceSlot` + quantity, delegating vocabulary to `ResourceRepository`), `resolve_quantity()`, `normalize()`. These back **only** the Mock provider and real-provider fallbacks — no node calls them on the live LLM path.
- `intent.py` — `TopIntent`, `CommandLabel` enums + strict structured-output models (`TopClassification`, `CommandClassification`).
- `dialogue.py` — `DialogueSpec`, `SCENE_GUIDE` (includes `"situation"`), `sanitize` (empty/overlong reject, numeric-fact/situation guard), `render` (fallback boundary), and `SurfaceProfile` / `SURFACE_PROFILES` (below, now also carrying a `situation: str` fallback line per surface — the `react` fallback when the LLM fails or the provider is Mock). Fallback text is never put in a prompt.
- `gametime.py` — turns the client-owned `TimeContext` into a Korean `[상황]` prompt line. Unknown period labels fall back to the supplied hour; it does not participate in routing. Shared by `graph.py`'s `say()` and `situation.py`'s `build_spec` — it is not exclusive to the chat path.
- `companions.py` — `CompanionProfile` / `COMPANION_PROFILES`, a `dict[str, CompanionProfile]` mirroring `SURFACE_PROFILES`'s shape as the extension point for a second persona. Today it holds one entry (`"mako"`) and nothing reads `CompanionProfile.display_name` yet — adding a real second companion means giving `llm.py` a per-companion prompt table (today's `_DIALOGUE_PROMPT_TEMPLATE` and memory prompts are Mako-only strings) and threading `companion_id` into `say()`/`graph.py`'s state, not just adding a dict entry here.
- `recipes.py` / `enemies.py` / `lore.py` — `RecipeRepository` / `EnemyRepository` / `LoreRepository`: verified-fact stores queried before dialogue so game info is never invented. `RecipeRepository` reads the pure ERD dataset from `app/gamedata/dataset.py` and covers 13 general recipes plus 4 smelting paths; `EnemyRepository` covers the 3 seeded enemies and their aliases, weak elements, weak parts and advice. Both remain synchronous and DB-free because the graph is compiled once at app startup. Lore is keyed by `location_id` (currently only `region_abandoned_mining_village`), which the adapter reads out of `game_context` and puts on `CompanionTurn`.
- `resources.py` — `ResourceId` (`wood`/`stone`), `ResourceRepository`, `GatherParameters`, `MAX_GATHER_QUANTITY`. Owns the gatherable-resource **allowlist** (canonical id → player-facing aliases) and the quantity ceiling. Aliases match on particle boundaries (`(?:^|\s)돌(?:을|를|…)?(?=\s|$)`). `find_all()` returns every resource mentioned, not the first; two or more distinct resources ask back rather than picking one, and the same rule is written into `_COMMAND_ROUTER_PROMPT`.
- `facts.py` — `DialogueFact` model shared by the verified recipe, enemy and lore repositories.

## Memory rules

There are **three memory layers with different lifetimes, and they are never mixed** — one record with two writers on different clocks can satisfy neither one's rules.

| | L0 transcript | L1 working memory | L2 long-term memory |
|---|---|---|---|
| module | `transcript.py` | `store.py` | `memory.py` |
| key | `conversation_key` | `conversation_key` | HMAC `player_key` (profile + save slot) |
| holds | every line, verbatim | ask-back slot + last few turns | profile facts, episodes, session summaries + optional vectors |
| lifetime | a JSONL per conversation; swept past `TRANSCRIPT_RETENTION_DAYS` | idle TTL, then gone; dies with the process | SQLite `episodic_memories`; only the count cap evicts |
| written | every turn, after the reply, off the loop | every turn, synchronously, inside the conversation lock | in the background loop, never in a turn |
| prompt block | none — it feeds distillation, not dialogue | `[최근 대화]` | `[기억]` |

**L2 is derived from L0, not a side effect of a turn.** The brain holds a cursor per conversation (`_Pending`) and one background loop reads the un-distilled span and moves the cursor forward. That is what buys retry, resume, and re-distillation; a turn-counter modulo could offer none of them.

Rules that hold for all three: keys are **opaque** (never a raw player name), caps are **constants, not settings** (`MAX_HISTORY_TURNS` / `MAX_HISTORY_TEXT`, `MAX_MEMORIES_PER_PLAYER` / `MAX_MEMORY_TEXT`, `MAX_SUMMARY_TURNS`, `MAX_EXTRACT_ENTRIES`, `MAX_PENDING_CONVERSATIONS`, `HALF_LIFE_DAYS` — a limit you can raise with an environment variable is not a limit), none of it reaches the **structured log stream**, and what reaches a prompt reaches **`say()` only** — never a classifier.

### The distillation pipeline

One in-memory queue and one loop. `_run` only sleeps and calls `_drain(now=…)`; **every timing decision lives in `_drain`**, which is why tests pass a clock and never sleep. Three triggers:

| condition | what happens |
|---|---|
| un-distilled entries ≥ `N × 2` | incremental extraction (profile · episode) |
| quiet for `LONG_TERM_QUIET_SECONDS` (90) with anything pending | incremental extraction — **this is what kills tail loss**; a 2-turn conversation still leaves a memory |
| quiet for `LONG_TERM_SESSION_END_SECONDS` (600) | one session summary, then the entry leaves the queue |

`aclose()` cancels the loop, drains once with `final=True`, and only then closes the provider — a clean shutdown loses no tail. **The queue is in-memory**: a restart drops the cursors, so an un-distilled tail is skipped by the automatic pipeline. The transcript survives, so a bulk re-distillation is still possible — which was not true before L0 existed.

Rules specific to long-term memory:

- **It is not a fact source, and it must not be able to become one.** It rides in `DialogueSpec.memories`, never `facts`. `sanitize` would reject any dialogue echoing a number that is not in `facts`, so `build_memory` **refuses to store a candidate containing a digit** — that keeps the numeric guard untouched and stops a recalled memory from silently costing every affected turn its dialogue. The memory prompts are told to write quantities in words for the same reason.
- **Summarising is not extraction.** Incremental extraction sees only the span since the cursor, so asking it to summarise would yield "a summary of the last few exchanges" wearing the name of the whole conversation. `summarize_session` reads the transcript's tail (`MAX_SUMMARY_TURNS`) once, at session end.
- **Consolidation can never delete a memory.** It runs only at the cap, the *brain* calls the LLM (the store never does), and `consolidated()` returns `None` — leaving the originals untouched — on an empty result, an out-of-range source index, no line surviving `build_memory`, or a result that did not actually shrink. Merged lines inherit their sources' `created_at`/`recall_count`/`recalled_at`/`importance`, or decay would restart from zero every time.
- **Recall feedback is persisted.** `recall` with a non-empty query stamps `recalled_at`/`recall_count` in
  the SQLite row. An empty query is a "what do you know" scan (the `known` list, the consolidation
  input) and deliberately does not count. The legacy file store keeps the old best-effort behavior
  only for migration/backward-compatible tests.
- **The brain works without any of it.** `CompanionBrain(llm)` with no `long_term` store recalls and extracts nothing. Without a `transcript` store it still recalls but never extracts — distillation is a cursor over a log that does not exist. A `CompanionTurn` with an empty `player_key` does the same, per turn.
- The graph gets **already-recalled strings**, not the store. `build_companion_graph`'s signature is unchanged; a node cannot query memory, so no future node can accidentally give a classifier access to it.
